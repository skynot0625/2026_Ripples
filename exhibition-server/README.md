# Ripples ToF Web Viewer

Raspberry Pi 4 + Arducam B0410(240×180, 최대 4000mm) 깊이 영상을 브라우저로 보내는 헤드리스 뷰어.
기본 화면은 WebSocket으로 깊이 데이터를 받아 Canvas에 직접 그린다. MJPEG(`/stream.mjpg`)은 비교·호환용으로 남아 있다.
의존성: Python 표준 라이브러리, OpenCV, NumPy, ArducamDepthCamera.

## 전시 시스템 베이스: 운영 화면 + 프로젝터 화면 (mock)

전시용으로 확장하기 위한 최소 베이스다. 하나의 `server.py`가 아래 화면을 모두 제공하고, 같은 컴퓨터나 LAN의 다른 기기에서 동시에 열 수 있다.
인터넷 연결 없이 동작한다(CDN·외부 폰트·외부 스크립트 없음). Mac, Windows, Linux에서 같은 명령으로 실행한다.

### 화면 구조 (2026-10-15)

사용자 메뉴에는 아래 여섯 화면만 있다. 실제 출력(기구 화면·블라인드 출력)은 출력 관리에서 연다.

| `/simulator` | 시뮬레이터 | 혈·맥 조작. 위 절반은 선택한 장치의 "기구 화면" 또는 "블라인드 화면"(아래) |

**작업실 PC 3단 배치 (2026-11-02)** — 창 너비 1280 px 이상이면 왼쪽 = composition·레이어 목록·출력 배정·입력, 가운데 = 미리보기, 오른쪽 = 목록에서 고른 레이어 하나의 설정(따로 스크롤)이다. 목록에는 레이어 이름과 종류만 보이고 누르면 고른다. 레이어를 추가·복제하면 그 레이어가 골라진다. 1024–1279 px은 예전 2단(오른쪽 사이드바), 휴대폰은 예전 세로 배치, 편집 닫기·전체 화면·UI 숨기기는 미리보기만. 저장 형식·편집 기능은 그대로다.

**composition과 레이어** — 노드·케이블 없이 세로 레이어 목록으로 편집한다. 안에서는 입력(source) → 레이어 종류(renderer) → 레이어 → 출력으로 나뉘지만, 사용자는 레이어마다 입력과 종류만 고른다.

- 레이어 종류(`tofrender.js` RENDERERS): ToF SENSOR / CONTOUR / SIDE / RELIEF 45°(예전 네 모드의 그리기 코드 그대로, 서버가 그 레이어 설정으로 프레임을 만듦), 수치 막대 + 최근 10초(예전 맥 audio 진단 그리기, 아무 수치 입력에), 단색 면.
- 실험용 ToF 모드 4개(2026-10-15 오후, 레이어 종류 목록에만 있음 — 기본 composition·출력 슬롯에 자동으로 쓰이지 않고 작품 방향도 아님): 서버가 SIDE용으로 이미 보내는 깊이(시간 필터·5×5 median, far 밖 = 0)를 브라우저에서 그린다. 센서 데이터 형식·API는 그대로다. 측정값 없음은 항상 검정.
  - SILHOUETTE: 실루엣 시작~끝(mm) 범위 안을 흰색으로 채움, 반전 = 측정된 곳 중 범위 밖.
  - DEPTH BANDS: 거리를 띠 개수(2–24)로 나눠 먼 띠 색 → 가까운 띠 색, 띠 경계선(선택).
  - POINTS: 240×180 깊이를 간격(1–8)마다 사각 점으로, 점 크기, 가까울수록 크게/진하게(선택).
  - MOTION: 직전 프레임보다 감도(mm) 이상 바뀐 곳(새로 측정된 곳 포함)만 흰색, 사라지는 시간(초) 안에 선형으로 검정. 기본 감도 40 mm(정지 장면의 mock 잡음 최대 27 mm보다 큼).
  - NUMBERS(깊이 숫자, 2026-11-02): "숫자 간격"(4–30 센서 화소, 기본 10)마다 칸 가운데 화소 하나의 깊이를 숫자로 씀. 단위 cm(기본)·mm·m, 가까울수록 밝게(선택), 칸 선(선택). 측정값 없음은 숫자 없음. 서버가 SIDE용으로 보내는 필터된 깊이(시간 필터·5×5 median, far 밖 = 0)라 원본 한 화소 값과는 다를 수 있음. 글자가 4 px보다 작아지는 캔버스에서는 숫자를 그리지 않음
- 화소 표현(2026-11-02, 센서 화소마다 그리는 ToF SENSOR·SILHOUETTE·DEPTH BANDS·MOTION 레이어의 설정): 매끈하게(새 레이어 기본) = 깊이를 4배로 보간한 뒤 그 크기에서 색·띠·범위를 계산(윤곽이 센서 격자 계단 대신 깊이를 따라감). 보간은 측정된 이웃만 쓰고(주변 절반 미만이 측정이면 검정), 이웃 깊이 차가 150 mm보다 크면 섞지 않고 가장 가까운 측정값을 써서 사람과 뒤 벽 사이 같은 없는 깊이를 만들지 않는다. 부드럽게 = 완성된 그림을 브라우저가 bilinear로 확대(가장자리가 검정 쪽으로 번짐). 센서 칸 그대로 = 예전. 이 설정이 없는 저장된 레이어는 "센서 칸 그대로"로 읽혀 예전과 같다(서버도 값이 있을 때만 저장). 측정이 끝나는 가장자리(far 밖 = 0인 경계)는 매끈하게에서도 센서 격자를 따른다(그 밖은 측정값이 없음)
- 깎이는 매스(실험, 2026-11-02, ToF 레이어 종류 `tof_mass`, 기본 composition·출력에 자동으로 쓰이지 않음): 카메라 앞에 상자 모양 매스(카메라에서 "매스 앞면" m부터 "매스 두께" m, 너비 = 센서 70° 시야의 가운데 깊이 폭, 카메라와 같이 움직임)를 두고 ToF 깊이로 깎는다. 센서 화면을 "칸 크기" 화소 칸으로 나눠 칸마다 깎인 깊이를 기억하고, 새 깊이 프레임마다 칸 안의 가장 가까운 측정값으로 깎는다. 깎는 방식: 가까운 만큼 눌러 깎기("깎기 시작 거리"(기본 2.5 m)보다 먼 것은 안 깎고, ToF near에 가까울수록 두께 전부까지. 그래서 바닥·먼 벽은 매스를 깎지 않음) / 보인 빈 공간만큼 깎기(측정된 면 앞은 비어 있으므로 Z − 앞면까지). 흔적: 남았다가 다시 차오름(깎인 곳은 더 깊어지기만 하고 "다시 차오르는 시간"(기본 10 s) 동안 두께 전체가 차오름, 0 = 계속 남음) / 남기지 않음(매 프레임 지금 보이는 것만큼만 깎임). 측정값 없는 칸은 깎지 않는다. 비스듬한 시점(좌우·위아래 각도, 0/0 = 카메라에서)에서 앞면(칸 사이 부드럽게)과 옆면을 Canvas 2D로 그리고, 깎인 깊이만큼 "깎인 곳 색"으로 물든다. 화면은 새 ToF 프레임이 올 때만 다시 그린다. 누적된 센서 기록이며 학습값이 아니다
- 공간선(실험)(2026-10-15 밤, ToF 레이어 종류 `tof_spaceline`, 기본 composition·출력에 자동으로 쓰이지 않음): 센서가 지나오며 읽은 공간을 3D 선으로 누적하는 실험(누적된 센서 기록이며 학습값이 아님). 서버가 SIDE용으로 보내는 필터된 깊이를 브라우저에서 WebGL로 그린다(센서 형식·API 그대로).
  - 선 생성 방식은 하나만: 경계 윤곽(깊이가 "경계 기준" mm 이상 바뀌거나 측정값 없음과 만나는 곳의 테두리, 가까운 쪽 깊이) / 거리별 등고선(거리 "등고선 간격"마다, marching squares) / 점 연결선("점 간격"마다 이웃 점을 이음, 큰 깊이 차는 잇지 않음). 방식을 바꾸면 이전 방식의 선은 지운다.
  - 각 깊이 샘플은 카메라 좌표 점이 된다: mock ToF는 광선 방향 거리를 재므로 Z = r / √(1 + xn² + yn²), 화각 70°(mock_tof.py 가정값, 실제 B0410 화각 미확인). "기록 간격"마다 한 묶음.
  - mock 시뮬레이션(/inputs mock + /ws/simulator 혈 pose)이면 묶음을 그때 혈의 위치·방향(ToF 높이 1.5 m, 수평)으로 공간에 고정하고, 화면은 지금 혈의 카메라에서 본다 — 혈이 움직이거나 돌면 지난 선은 공간에 남고 화면에서 그만큼 움직인다. pose가 없는 실제 입력이면 카메라 좌표로만 그리고 작업실 카드에 "카메라 기준"이라고 쓴다(공간 고정·추정 pose 없음).
  - 깊이 버퍼로 가림(가까운 선이 먼 선 앞, 그린 순서와 무관). 묶음은 "고정 시간" 동안 제자리, 그 뒤 "처지는 시간" 동안 중력 방향(화면 방향, 0° = 위·시계 방향, 빠른 선택 위/오른쪽/아래/왼쪽, 기본 아래)으로 "중력 세기"(m)만큼 처지고 "뭉침"만큼 묶음 중심으로 모이며, 마지막 "사라지는 시간" 동안 흐려져 지워진다. 중력·뭉침은 오래된 선에만.
  - 아웃포커싱: 색과 실제 Z(선형 깊이)를 따로 그린 뒤 GPU에서 픽셀마다 초점면에서 떨어진 Z만큼 흐린다(화면 전체 같은 blur가 아님). 초점 = "초점 위치" 가로·세로(%, 기본 화면 가운데)의 ToF 깊이 Z + "초점 거리 보정", "선명한 깊이 범위", "아웃포커싱 강도"(px, 0 = 끔). 가까운 선/먼 선 색.
  - 확인용 계수(화면에는 안 보임, 합성기 `status(레이어 id)`): 만든 묶음·선 수, 마지막 묶음의 상한 전/후 선 수, 지운 묶음(수명·상한·reset)과 마지막 reset 이유, 초점 Z.
  - 상한: 묶음 160개, 묶음당 선 6,000개, 전체 240,000개(넘으면 오래된 묶음부터 지움), 수명 = 고정 + 처짐 + 사라짐(최대 80초). WebGL 선 두께는 대부분 1px이라 고밀도 화면에서는 1.5배 밀도까지만 그린 뒤 늘린다. 클라이언트의 pose는 시뮬레이터 상태 한 번(수십 ms) 늦을 수 있다. WebGL이 없으면 그 레이어에 그렇다고 쓰고 그리지 않는다.
- 천장 거리 센서 레이어 4개(2026-10-15 저녁, 레이어 추가 목록의 "천장 거리 센서" 묶음): 입력은 서버에 이미 있는 `/inputs` → `channels.distance`(`value` m, `connected`, `seq`, `age_s`, `paused`) 그대로 = 소스 `sensor.up_distance`. 목 모드에서는 서버가 시뮬레이터의 혈 위치에서 M30 천장까지의 거리로 이 값을 만든다(천장을 모르면 값 없음). 단일 거리값을 ToF 영상처럼 만들지 않고 전용 그림으로 그린다. 측정값 없음(연결 끊김·값 없음·아이들링으로 수집 멈춤·서버 끊김)이면 그 레이어는 바로 검정, 값을 지어내지 않는다.
  - VERTICAL METER(세로 막대): 입력 범위 안의 거리 = 막대 높이(반전 = 가까울수록 높게), 두께.
  - PULSE(파동): 거리 = 원 크기, 거리 변화 속도 = 밝기·불투명도·퍼지는 빠르기. 크기, 반복 수, 변화 감도, 감쇠(초). 선 두께는 2 CSS px로 고정이다(2026-10-15 밤부터 센서값으로 바뀌지 않음, 예전에는 변화가 크면 최대 3배로 굵어졌음).
    - 둘레(2026-10-15 밤): 이 센서는 단일점이라 방향별 천장 형상은 재지 않는다. 둘레는 그 한 점 거리의 최근 "둘레에 놓는 시간"(1–30 s, 기본 6 s) 기록을 시간 순서로 한 바퀴 놓은 것이다(위 = 지금, 시계 방향 = 과거). 각 점의 반지름 = 1 + "둘레 왜곡 세기"(0–1, 기본 0.35) × tanh("둘레 왜곡 민감도"(0.1–20 /m, 기본 2) × (구간 평균 − 그때 거리)). 그래서 입력이 일정하면 원이고, 최근 변화가 클수록 둘레가 불규칙해진다. 평균보다 가까웠던 때가 바깥쪽이다("가까울수록 크게"와 같은 방향, 반전이면 반대). 부드럽게 설정은 다른 모드와 같다. 측정이 없던 구간과 첫 값 이전은 원 위에 둔다(값을 지어내지 않음).
    - 저장값에 이 세 설정이 없는 이전 PULSE 레이어는 세기 0으로 읽어 예전처럼 원이다(서버도 없는 값을 채워 넣지 않음). 새로 추가하는 PULSE는 위 기본값으로 시작한다.
    - 시각 실험(색상 매핑·단계·픽셀화·블러/글로우·대칭·잔상·잔상 간격)을 ToF 레이어와 같은 코드·순서로 PULSE에도 적용한다(`layer.effects`). 크기 단위는 레이어를 240×180으로 볼 때의 1칸이다. 다른 천장 센서 모드(METER·TRACE·FIELD)에는 붙이지 않는다.
  - HISTORY TRACE(시간 기록): 받은 값을 측정 시각(도착 − age_s)에 찍어 오른쪽 = 지금, 표시 시간(5–120초), 선 두께, 아래 면 채우기, 잔상(오래된 부분 흐리게). 측정값 없던 구간은 끊김으로 보이고, 지난 실제 값은 표시 시간 동안 남는다.
  - DISTANCE FIELD(흐름 띠): 화면 전체의 띠가 흐른다. 거리 = 띠 간격(가까울수록 촘촘), 변화량 = 흐르는 속도. 띠 수, 속도 감도, 선명도, 흐르는 방향(빠른 선택 위/오른쪽/아래/왼쪽 = 0/90/180/270°, 미세 조절 0–359°, 0° = 위·시계 방향, 방향은 띠를 돌리기만 하고 간격·속도 반응은 그대로).
  - 공통 설정(레이어마다 따로 저장): 입력 최소/최대(m), 부드럽게, 변화량 강조, 반전, 가까움/중간/멀어짐 색과 중간 지점.

  - 시뮬레이터 위치가 없으면(실제 입력) 카메라 기준으로 센서 앞쪽만 위에서 본 모습을 그리고 지도·누적·천장 trace는 없다.
  - 화면마다 따로 쌓는다 : 작업실 미리보기와 시뮬레이터 혈 블라인드(그리고 출력 창)는 같은 그리기 규칙이지만 각자 연 순간부터 흔적을 쌓는다(서버에 저장되는 흔적 없음). 색·겹침·수명은 실험 설정값이며 최종 디자인이 아니다.

**맥 마이크 3개 가상 입력**(2026-10-29, mock): 사용자 확정 = 맥에 가까이 붙은 마이크 3개. 그 밖은 mock용 가정값이다(실제 모델·간격·배치·동기화·데이터 형식 미정). `/inputs` → `channels.maek_mic`, 값 = 같은 순간의 `[마이크 1, 2, 3]` 레벨 0–1(30–90 dB SPL 가정), 30 Hz. 가정 배치 : 맥 pose 중심 반지름 100 mm 원 위 정삼각형(마이크 사이 약 17 cm), 높이 1.2 m, 마이크 1 = 맥 진행 방향, 2·3 = +120°·+240°. 소리 = 시뮬레이터 관람객이 무작위로 말하는 소리(1 m에서 약 62 dB, 입 높이 1.55 m) + 실내 바닥 소음 36 dB, 각 마이크까지 거리 제곱으로 줄어듦(벽 반사·도달 시간 차 없음) + 마이크마다 작은 잡음. 가까운 소리는 세 마이크 값이 달라지고(0.6 m 앞 관람객: 그쪽 마이크가 약 1.7 dB 큼) 먼 소리는 거의 같다. 작업실 입력 `maek.mic1`·`maek.mic2`·`maek.mic3`(숫자)로 모든 레이어의 입력·연결에 쓸 수 있고, 출력 관리 표에 한 줄. 방향·위치 추정은 방식이 정해지지 않아 만들지 않음. 기존 `audio` 채널(맥 기구 화면의 레벨 하나)은 그대로.

**PC 배치**(2026-10-20): 창 폭 1024px 이상이면 작업실은 미리보기 왼쪽·편집 패널 오른쪽 사이드바(따로 스크롤), 시뮬레이터는 미리보기 왼쪽(헤더 아래 남은 높이 전부)·혈/맥·화면 선택·보기 설정·조작부 오른쪽 열, 블라인드 맵핑은 모서리 작업 영역 왼쪽·툴바와 패널 오른쪽 사이드바. 1024px 미만(휴대폰·좁은 창)은 예전처럼 위아래로 쌓는다. PC에서 메뉴(≡)는 헤더를 늘리지 않고 버튼 아래에 겹쳐 뜨는 드롭다운이다(휴대폰은 예전처럼 헤더에 붙어 펼쳐짐). 편집·확인 화면(`/`, `/operator`, `/simulator`, `/mapping`, `/venue3d`)은 `?test`·`?clean`·`?embed` 없이 열면 서버가 같은 주소의 `?test`로 넘겨(302) 항상 뒤로·메뉴가 있다. 전시 출력(`/display/…&clean`)·시뮬레이터 안 화면(`?embed`)은 그대로. 작업실의 편집 닫기·전체 화면·UI 숨기기, 맵핑의 UI 숨기기에서는 미리보기/작업 영역이 창 전체를 쓴다.

**시뮬레이터의 서버 CPU / GPU 표시**(2026-10-15 밤): 맨 위 줄 오른쪽 "뒤로/메뉴" 버튼 왼쪽에 작은 두 줄로 "서버 CPU nn% / GPU nn%"가 나온다. 이것은 server.py를 실행 중인 컴퓨터의 사용률이고, 보고 있는 휴대폰의 값이 아니다. `/api/host`(host_stats.py)는 누가 요청한 뒤 30초 동안만 백그라운드 스레드로 2초마다 잰다. 요청은 캐시만 읽어서 센서·렌더 흐름을 막지 않는다. 화면은 3초마다, 보일 때만 묻는다.
  - CPU = 전체 코어 사용률. Windows는 GetSystemTimes, macOS는 host_statistics, Linux는 /proc/stat을 쓴다(추가 패키지 없음).
  - GPU: NVIDIA는 nvidia-smi `utilization.gpu`로 잰다(전시컴 RTX 5060 Ti). Apple GPU는 ioreg `Device Utilization %`로 잰다. 그 밖의 GPU(전시컴의 AMD 내장 GPU 등)는 읽지 않는다.
  - 읽을 수 없으면 0이 아니라 "--"로 표시하고, 이유는 툴팁에 쓴다. 출력 화면(`/display/…`)에는 없다.

**시뮬레이터의 기구 화면 / 블라인드 화면** — (2026-10-15 밤 배치) 맨 위 내비게이션(장소·서버 CPU/GPU·뒤로·메뉴) 바로 아래에 미리보기가 붙어 화면 폭 전체와 남은 높이를 모두 쓴다(375×812 489px = 60 %, 390×844 521px = 62 %, 1280×800 477px, 1440×900 577px; 맥은 접속 버튼이 없어 더 큼). 미리보기 위에는 아무것도 겹치지 않는다 — 그 아래로 차례로 혈/맥·기구 화면/블라인드 화면·⚙ 한 줄, 열었을 때만 보기 설정 줄, 연결이 끊겼을 때만 안내 줄, 이동·회전·접속 조작부(버튼 44px 이상, 짧은 화면에서는 안에서 스크롤). 미리보기 안의 페이지(출력 주소 그대로)는 자기 비율로 그려져 잘리거나 늘어나지 않는다(출력 페이지 배치는 바꾸지 않음). 기구 화면 = `/display/hyeol` 또는 `/display/maek`. 블라인드 화면 = 블라인드 맵핑의 배정(`mapping.assignment`)이 지금 그 기구에 준 공간의 블라인드 composition(`/ws/visual`의 그 역할 블라인드 슬롯)이고, 혈 ↔ 맥 교환 시 기구를 따라간다.
- 프로젝터 보기(⚙ 보기 설정, 저장 안 함, 페이지를 열 때마다 "시각화"): 시각화 = 배정된 composition을 맵핑 없이 그 부스 master canvas 비율로 최대한 크게(`/display/blind?space=a|b&embed`). 맵핑 확인 = 같은 composition을 저장된 블라인드 맵핑(분할·간격·surface 변형)으로(`…&clean&embed&mapcheck`, 부스 "출력 내용"이 테스트 패턴이어도 composition으로 보여 줌).
- 실제 프로젝터 창(`/display/blind?space=a|b&clean`)은 전처럼 부스 "출력 내용"을 따른다 — "테스트 패턴"이면 패턴, "배정된 composition"(예전 이름 "진단 화면")이면 배정된 composition을 맵핑해 출력. 블라인드 맵핑 화면은 공간마다 배정된 composition 이름을 같은 배정·슬롯에서 읽어 보여 준다(편집 미리보기는 계속 테스트 패턴).
- 화면을 바꿔도 서버에 아무것도 보내지 않으므로 기구 위치·방향·접속 상태, mapping, composition 배정은 그대로다.

### 설치 (개발용 Mac / Windows / Linux)

Python 3.9 이상이 필요하다. 처음 한 번만, 인터넷이 되는 곳에서 설치한다(이후 실행은 오프라인 가능).

```bash
cd tof-web-viewer
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Windows에서는 `python3` 대신 `python`을 쓴다. 라즈베리파이의 실제 카메라 실행에는 기존처럼 `~/tof-env`와 ArducamDepthCamera가 필요하다(아래 "실행 (라즈베리파이)").

### mock mode 실행

```bash
source .venv/bin/activate          # Windows: .venv\Scripts\activate
python server.py --mock
```

`--mock`은 센서형 ToF 테스트 프레임(아래 "ToF mock")과 함께 20m 거리 센서, audio, AI/LED의 mock 입력도 켠다.
`--mock` 없이 실행하면 ToF는 실제 카메라를 쓰고, 나머지 세 입력은 아직 receiver가 없으므로 운영 화면에 `none` / `입력 없음`으로 표시된다.

### 한 컴퓨터에서 세 화면 테스트하는 순서

1. 터미널에서 `python server.py --mock` 실행. `Operator: http://localhost:8000/operator`가 출력된다.
2. 브라우저에서 `http://localhost:8000/operator`를 연다.
3. 상단에 `● 서버 연결됨`, `MOCK MODE (--mock)`가 보이는지 확인한다.
4. 표의 네 줄(ToF camera, 20m 거리 센서, audio, AI / LED)이 모두 `● 정상`, source `mock`인지 확인한다. ToF는 약 30 fps, 거리 센서 약 10 Hz, audio 약 30 Hz, AI/LED 1 Hz(heartbeat 번호 증가).
5. `OUTPUT A 새 창` 클릭 → 방 안을 걷는 사람이 움직이고, 왼쪽 위 `frame #`이 계속 늘며 `갱신 중`으로 표시되는지 확인한다(멈추면 빨간색 `정지`).
6. `OUTPUT B 새 창` 클릭 → 막대 길이와 그래프가 계속 변하는지 확인한다(약 3초마다 짧게 튀는 값이 보인다).
7. `ToF viewer 새 창`(또는 `http://localhost:8000/`)에서 SENSOR/CONTOUR/SIDE/RELIEF 45°를 눌러 보면, 기존 화면과 함께 OUTPUT A도 같은 모드로 바뀐다.
8. 서버를 `Ctrl+C`로 끄면 운영 화면은 `서버 연결 끊김`(빨간색), output 화면은 빨간 진단 문구로 바뀐다. 서버를 다시 켜면 자동으로 복구된다.

브라우저가 팝업을 막으면 주소창 오른쪽의 팝업 허용을 누르거나, 위 URL을 새 탭에 직접 입력한다.
창을 프로젝터 모니터로 옮긴 뒤 더블클릭하면 전체 화면이 된다.

### LAN의 다른 기기에서 접속

서버는 기본으로 모든 네트워크 인터페이스(`0.0.0.0`)에서 받는다.

1. 서버 컴퓨터의 IP를 확인한다. Mac: `ipconfig getifaddr en0`, Windows: `ipconfig`(IPv4 주소), Linux: `hostname -I`.
2. 같은 네트워크의 다른 기기 브라우저에서 `http://<IP>:8000/operator`(출력 관리)를 열고 거기서 기구 화면·블라인드 출력을 연다.
3. 접속이 안 되면 서버 컴퓨터의 방화벽에서 Python의 8000번 포트 수신을 허용한다(Mac은 처음 실행할 때 허용 여부를 묻는다. Windows는 "Windows Defender 방화벽" 알림에서 개인 네트워크 허용).

포트를 바꾸려면 `python server.py --mock --port 8080`.

### 구조

```text
inputs.py   InputChannel (입력마다 최신값 1개만 보관) + MockSource (mock 값을 주기적으로 update)
server.py   /inputs → { mock, tof: {...}, channels: { distance, audio, ai_led } }  (JSON)
operator.html, output_b.html → /inputs를 조회 (한 번에 요청 1개, 응답 전이면 다음 조회를 건너뜀)
index.html (/, 작업실) · display.html (출력) → ToF 레이어마다 /ws?tof=<설정>, 수치 입력은 /inputs·/api/simulator · 모두 tofrender.js 합성기로 그림
```

- 모든 입력은 최신값 하나만 덮어쓴다. 큐가 없으므로 화면이 느리거나 여러 화면이 동시에 열려도 과거 값이 쌓이지 않고 건너뛴다.
- mock source와 화면은 분리되어 있다. 실제 장치가 정해지면 해당 채널의 `MockSource` 대신 receiver가 같은 `channel.update(value)`를 호출하면 된다.
- 각 채널의 `/inputs` 항목: `label`, `unit`, `source`(`mock` / `none`), `connected`(3초 안에 갱신됨), `value`, `seq`(갱신 횟수), `age_s`, `rate_hz`, `error`.
- mock 값의 모양(거리 m 숫자, audio 0–1 숫자, AI/LED는 값 없이 heartbeat만)은 테스트용이며, 실제 장치의 protocol이나 data format을 정한 것이 아니다.

```bash
curl -s http://localhost:8000/inputs | python3 -m json.tool
```

### 진행상황 페이지 (`/progress`)

- 작업 진행상황은 프로젝트 루트의 `PROGRESS.md`에 적는다. 순서: `## 현재 상태` → `## 작업 내역` → `## 막힌 것` → `## 다음 한 가지` → `## 사용자 결정이 필요한 것` → `## 참고`.
- 새 작업은 `## 작업 내역` 맨 위에 `### 날짜 · 작업 이름` 블록으로 쓰고, 그 안을 `#### 한 일` / `#### 확인한 결과` / `#### 목업·가정값` / `#### 폐기·이력`으로 나눈다(확인된 사실·목업·미결·폐기를 섞지 않음). 기존 블록은 지우거나 옮기지 않는다 — `/progress`가 맨 위 블록 하나만 "최신 작업 내역"으로 펼치고, 나머지는 자동으로 "이전 작업 내역"의 접힌 토글로 보여 준다. `현재 상태`·`막힌 것`·`다음 한 가지`·`사용자 결정이 필요한 것`은 매번 지금 사실로 고쳐 쓴다.
- 다른 섹션에서 `### ` 하위 목록(보류, 그 외 미결, 참고)은 접힌 토글로 보이고, 그 앞 글은 바로 보인다.
- `PROGRESS.md`를 갱신하면 서버 재시작 없이 `http://<서버>:8000/progress`를 새로고침해서 바로 확인할 수 있다(휴대폰용 텍스트 페이지).
- 확인된 사실만 적는다. password, token, 개인 정보, 임시 파일 경로는 적지 않는다.
- `/progress`는 휴대폰용 화면이다. 상단 고정 header에 mock·ToF 상태와 수정 시각이 글자로 보이고, `메뉴` 버튼(넓은 화면에서는 바로 보이는 링크)으로 모든 사용자용 화면을 `?test` 상태로 연다. 본문 맨 위에 `다음 한 가지`(복사본)와 현재 상태가 있고, header의 섹션 링크로 `막힌 것` 등으로 바로 이동한다. 토글은 제목 줄 전체(높이 48px 이상)를 눌러 열고 닫으며, `/progress#hist-2` 같은 링크는 그 토글을 열어서 보여 준다.
- 새 사용자용 HTML 페이지나 화면 route를 추가할 때마다 `server.py`의 `NAV_LINKS`에도 반드시 같이 추가한다. 이 목록이 `/progress` menu와 각 화면의 test UI menu에 함께 쓰인다. 새 화면에는 `<script src="/testui.js"></script>`를 넣는다. `/inputs` 같은 JSON endpoint는 넣지 않는다.

### test / clean 진입 방식 (`/`, `/operator`, `/display/…`, `/mapping` 등 공통)

| URL | 상태 |
| --- | --- |
| `<화면>?test` | 휴대폰 테스트 UI. 오른쪽 위 `‹ 뒤로`와 `메뉴`(화면 이름, mock·ToF 상태, `UI 숨기기`, `전체 화면`, 다른 화면 링크) |
| `<화면>?clean` | 전시용 출력. 뒤로 버튼·메뉴·조작부·진단 글자를 모두 숨기고 시각 출력만 남김. `/output/<역할>?space=a|b&clean`은 그 공간(부스)의 master canvas를 블라인드 구성대로 잘라 warp해서 출력 |
| `<화면>` (query 없음) | 기존 동작 그대로 |

- `UI 숨기기`: 화면의 조작부와 메뉴를 숨기고 `‹ 뒤로`와 `UI 보이기`만 남긴다(`/mapping`의 E 키와 같은 상태).
- `메뉴`: 항목이 화면보다 길면 메뉴 안쪽만 세로로 스크롤되고 `‹ 뒤로`·`닫기`는 위에 그대로 남는다. 높이는 실제로 보이는 화면(iPhone Safari의 주소창·하단 바·safe area 제외) 기준으로 메뉴를 열 때와 화면 크기가 바뀔 때 다시 맞춘다. `/progress` 메뉴도 같다.
- `‹ 뒤로`: 전체 화면이면 먼저 끝낸 뒤, 이 서버에서 온 기록이 있으면 브라우저 뒤로, 직접 연 경우에는 `/progress`로 간다.
- iPhone Safari는 페이지 전체 화면을 지원하지 않아 메뉴의 `전체 화면` 버튼이 꺼지고 이유가 표시된다.
- `/mapping`은 query 없이 열어도 `?test`와 같은 편집 화면(위 메뉴 영역만 없음)이다. 휴대폰에서는 모서리 점 주변(지름 약 52px)을 눌러 끈다.

### 부스 mapping (master canvas + 블라인드)

부스 2개(A, B)가 각각 하나의 큰 master canvas를 가지고, 여러 블라인드(surface)가 그 일부를 나눠 보여준다. 설정은 브라우저가 아니라 **서버가 가진 값이 기준**이다.

| 화면 | 역할 |
| --- | --- |
| `/mapping?test` | 휴대폰 편집 화면. 위 메뉴 / 가운데 미리보기(작업 영역) / 아래 도구줄이 겹치지 않음 |
| `/display/blind?space=a&clean` | 공간(부스) A projector 창 (UI 없음, exhibition.json 기본값). 배정이 바뀌면 같은 창에서 다른 역할의 블라인드 composition으로 바뀜 (옛 `/output/hyeol?space=a&clean`도 같은 출력) |
| `/output/maek?space=b&clean` | 공간(부스) B projector 창 (UI 없음, exhibition.json 기본값) |
| `/mapping?clean&booth=a` | 부스 테스트 패턴만 전체 화면으로 (UI 없음) |

- 편집: `부스 A/B` 선택 → `미리보기`에서 테스트 패턴 또는 현재 배정된 실제 블라인드 composition 선택 → 블라인드 이름 버튼으로 선택(또는 미리보기에서 테두리 안을 누름) → 선택한 블라인드의 모서리 1–4를 끌어 warp. 미리보기 선택은 편집 화면에만 적용되고 저장되지 않으며, 두 모드 모두 같은 코너·실측 비율을 보여준다. `블라인드 추가`, `블라인드 설정`(이름, master canvas에서 가져올 영역의 왼쪽·위쪽·너비·높이, 모서리 초기화, 두 번 눌러 삭제), `부스 설정`(간격 포함/무시, 출력 내용, master canvas 비율, 원본 확대).
- 간격 포함 / 간격 무시: 같은 저장값(블라인드마다 실제 간격을 포함한 위치 `rect`)에서 화면 결과만 바뀐다. 간격 포함은 `rect`를 그대로 잘라 블라인드 사이 빈 공간도 master canvas 좌표에 포함하고, 간격 무시는 블라인드가 덮지 않는 빈 공간을 빼고 master canvas 전체를 블라인드에만 펼쳐 영상을 바로 이어 붙인다. 최종 방식은 정하지 않았다.
- 출력 내용: `테스트 패턴`(이어짐 확인용 격자·대각선·원·움직이는 선, 안내 줄에 현재 배정된 역할 이름) 또는 `진단 화면`(그 공간에 배정된 역할의 블라인드 composition을 master canvas로 사용, 기본값은 혈 = SENSOR, 맥 = audio 레벨). 이 선택은 공간 설정이라 교환해도 그대로다. 편집 화면 미리보기는 항상 테스트 패턴이다.
- 혈/맥 로테이션: 공간 A·B와 역할(혈·맥)은 분리되어 있다. 처음 배정은 A = 혈, B = 맥. 편집 화면의 `혈 ↔ 맥 교환`을 한 번 누르면 대기("한 번 더 누르면 교환", 3초), 두 번째에 적용된다. 교환하면 배정만 바뀌고 각 공간의 블라인드·모서리·간격·projector 창은 그대로다. 공간 창(`/display/blind?space=a|b&clean`)은 같은 창 안에서 새 역할의 블라인드 composition으로 바뀐다(주소는 그대로). 혈·맥 기구 화면은 이 routing과 무관하다.
- 블라인드 실측 크기(2026-10-15 밤, `블라인드 설정` 안 "실제 크기"): 블라인드마다 실제 가로·세로를 같은 단위로 입력한다(단위는 자유, 비율만 씀, 휴대폰 숫자 키패드, Enter·칸 벗어남 = 저장, Escape = 되돌림, 비우면 그 값 지움, 0·음수·문자는 받지 않음). 저장은 그 블라인드의 `real_w`/`real_h`(값이 있을 때만, 서버도 0 초과만 받음). 두 값이 다 있으면 실제 종횡비(가로 ÷ 세로)를 보여 주고, 그 블라인드가 master canvas에서 가져오는 영역(crop) 안의 가운데를 그 비율로 좁힌 평면 = 왜곡 전 콘텐츠 평면을 기존 모서리 4개가 투시 변형한다(편집 미리보기·출력 창·시뮬레이터 맵핑 확인 모두 같은 mapout.js). 모서리·저장 영역은 움직이지 않고 실측과 따로 저장된다. 패널의 작은 그림에서 왼쪽 = 왜곡 전 기준 형태(실측 비율, 실측 없으면 저장 영역 비율을 점선으로), 오른쪽 = 모서리 맵핑 뒤 형태(투시 포함, 이 편집 화면 기준 겉보기 비율)를 나눠 본다 — 실측이 납작하면 스크린 자체 비율, 실측보다 모서리 사각형이 납작하면 투시(설치 거리·각도). 실측이 없는 블라인드(이전 파일 전부)는 예전과 같은 crop·변형(사용자 맵핑으로 캔버스 크기·변형 값 동일 확인).
- master canvas 비율(가로 ÷ 세로), 블라인드 수·위치·크기·간격은 설치 당일 값으로 바꾼다. 지금 값(비율 2.0, 블라인드 2개)은 임시 기본값이다.
- 원본 확대(비율 유지): 블라인드 안에 들어가는 원본 시각화의 좌우가 비어 보일 때 master artwork 전체를 중심 기준으로 0–100% 확대한다. 가로·세로에 같은 배율을 써서 종횡비와 블라인드 사이의 이어짐을 유지하고, 확대된 바깥 부분만 잘린다. 코너·블라인드 모양·실측 비율은 움직이지 않으며 테스트 패턴에는 적용하지 않는다. 기존 파일은 0%로 읽혀 예전 출력과 같다.
- 현장 사용: 휴대폰을 전시 컴퓨터와 같은 LAN에 연결하고 `http://<전시PC_LAN_IP>:8000/mapping?test`를 연다(IP는 코드에 고정하지 않음). 인터넷·Tailscale·개인 계정 없이 동작한다.

#### 저장 파일

`data/mapping.json` (server.py가 있는 폴더 기준 상대 경로, macOS·Windows 공통. 다른 위치는 `python server.py --mapping-file <경로>`. 전시 실행 설정 `exhibition.json`은 venue별 파일 `data/m30/mapping.json`을 쓴다):

```json
{"version": 2, "revision": 12, "updated_at": "2026-10-13T17:05:00+09:00",
 "booths": {
   "a": {"name": "부스 A", "aspect": 2.0, "gap_mode": "include", "content": "pattern", "source_zoom": 1.0,
         "surfaces": [{"id": "1", "name": "블라인드 1",
                       "rect": {"x": 0.0, "y": 0.0, "w": 0.45, "h": 1.0},
                       "corners": [[x, y], [x, y], [x, y], [x, y]]}]},
   "b": {"...": "같은 형식"}},
 "assignment": {"a": "hyeol", "b": "maek"}}
```

- `assignment`: 공간마다 보여줄 역할 화면(`hyeol` 혈 / `maek` 맥, 서로 달라야 함). 이 필드가 없는 기존 version 2 파일은 A = 혈, B = 맥으로 읽고, 파일은 다음 저장 때 이 필드가 더해진다.
- 공간 `a`의 projector 창은 `/display/blind?space=a&clean`, `b`는 `/display/blind?space=b&clean`으로 연다(배정을 따라 블라인드 composition이 바뀜). `rect`는 master canvas 안의 0–1 영역, `corners`는 출력 화면의 0–1 좌표(TL·TR·BR·BL). 편집 화면에서는 작업 영역 기준, `?clean` 출력에서는 전체 화면 기준으로 같은 값을 그린다. 부스당 블라인드 1–16개.
- `source_zoom`은 원본 시각화의 균일 확대 배율 1–2(화면 표시는 0–100%)다. 하나의 master artwork에 먼저 적용한 뒤 각 블라인드 영역을 잘라 연속성이 유지된다. 필드가 없는 기존 파일은 1로 읽는다.
- 이전 형식(version 1, 블라인드 2개 고정)의 파일은 서버가 읽을 때 부스 A의 블라인드 1·2로 옮기고(모서리 그대로), 원본을 `data/mapping.v1-backup.json`으로 남긴다. 첫 수정을 저장할 때 version 2로 바뀐다.
- 저장 시점: 드래그·슬라이더 중에는 약 0.05초마다 서버 메모리를 바꾸고(연결된 휴대폰·출력 화면 즉시 갱신), 파일은 마지막 변경 0.5초 뒤 저장한다. 손을 떼거나 버튼 동작(추가·삭제·간격·내용·비율·이름)은 바로 파일에 저장하고, 저장이 끝난 뒤 도구줄에 `서버에 저장됨`이 뜬다. `Ctrl+C`로 끄면 남은 변경을 저장하고 종료한다. 강제 종료하면 드래그 중 마지막 0.5초 안의 값은 잃을 수 있다.
- 안전장치: `.tmp`에 쓰고 fsync → 이전 파일을 `.bak`으로 복사 → `os.replace`. 잘못된 요청은 거부하고 저장값은 그대로 둔다. 시작할 때 파일이 손상되어 있으면 `mapping.json.corrupt-<시각>`으로 복사해 두고 `.bak`(마지막 저장 바로 전 값)을 읽는다. 둘 다 없으면 기본값.
- 통신: 편집 화면과 출력 화면은 `/ws/mapping` WebSocket 하나로 값을 받고 보낸다(ToF 영상 `/ws`와 별도, 추가 polling 없음). 확인용 HTTP: `GET /api/mapping`, `POST /api/mapping` (`{"op": {"op": "surface", "booth": "a", "id": "1", "set": {"corners": [...]}}}`; op는 `swap`(혈/맥 교환)·`booth`·`add`·`delete`·`surface`, 정의는 `mapping_store.py`).
- 예전 각 브라우저 localStorage(`ripples-mapping-v1`) 값은 읽지도, 덮어쓰지도, 지우지도 않는다. 메뉴 열림·전체 화면·UI 숨김은 저장하지 않는다.

### simulator (`/simulator`) · venue · 기구 화면

혈(ToF + 상향 20m 거리센서)이 실제 전시장 geometry 안에서 움직일 때 두 센서 mock이 어떻게 달라지는지 휴대폰으로 확인하는 화면. 지금 구현 범위는 **혈 + 갤러리 M30**이다(맥·파워플랜트는 아래 "미결·미구현").

| URL | 역할 |
| --- | --- |
| `/simulator?test` | 조작 화면. 위 절반 = 선택한 장치의 기구 화면(시각화 canvas만 휴대폰 확인용 1.18배 확대·가장자리 소량 crop, 상태 글자와 실제 출력에는 미적용), 아래 절반 = 혈/맥 선택 · 혈 기구 접속/해제 · 전진/후진 · 좌회전/우회전 · 좌이동/우이동 |
| `/display/hyeol?test` (옛 `/monitor/hyeol`) | 혈 기구 화면: "혈 기구 화면" 슬롯의 composition(기본 SENSOR) + 위쪽 거리값·최근 10초 변화 + 사용 중/아이들링 표시. AI 시각화가 아님 |
| `/display/hyeol?test&debug`, `/simulator?test&debug` | 혈 기구 화면 아래에 프레임 경로 진단 한 줄(디버그 전용): 서버 생성 fps(`/status`), 수신 fps, 표시 fps(위 "표시 N fps"와 같음), 같은 소켓의 WebSocket RTT, 요청→도착 시간, 프레임 크기(86.4 kB), 초당 전송량, 해석·그리기 시간, 목표 fps와 실제 대기. 위쪽 거리의 "갱신 N Hz"는 20m 센서 값 갱신 빈도로 ToF fps와 별개 |

기구 화면의 ToF 프레임 요청(debug 여부와 무관, 블라인드 출력은 프레임이 오면 바로 다음 요청): 목표 15fps(주기 1000/15 ms). 요청은 한 번에 하나만 보내고(프레임을 받은 뒤에만 다음 "next"), 다음 요청 전 대기 = max(0, 주기 − 이번 프레임의 요청→도착 시간). 가까운 접속은 약 66ms를 기다려 15fps를 넘지 않고, 휴대폰처럼 요청→도착이 긴 접속은 그만큼 덜 기다린다(2026-10-15 A안, 예전에는 도착 뒤 무조건 66ms 대기).
| `/display/maek?test` (옛 `/monitor/maek`) | 맥 기구 화면: "맥 기구 화면" 슬롯의 composition(기본 audio 레벨: 막대 + 최근 10초) + 마이크 입력 상태(현재 audio mock 값 하나). 마이크 3대(확정)의 채널별 표시는 아직 없음 |
| `/venue3d?test` | 공간 3D 확인 (11-06부터 전시 배치 편집, "눈높이로 보기"(화각 50/75/95°, 눈높이 1.1/1.6/1.75 m, 끌기 둘러보기, W/S·A/D·←/→·Q/E·휠로 이동, 벽 통과), 사진 색): venue geometry를 자유 회전·확대해서 보고, 혈·맥의 현재 위치·방향(혈은 ToF 시야와 상향 센서 선)을 같은 공간에 표시. 아래 이동 버튼은 `/simulator`와 같은 입력·규칙 |

(2026-10-15부터 혈·맥 센싱 모니터는 혈·맥 기구 화면 `/display/hyeol`·`/display/maek`이고, 옛 `/monitor/…` 주소도 같은 화면을 연다. AI 시각화 화면은 미구현.)

**venue는 실행 설정으로 고정** (`python server.py --mock --venue m30`, 전시 실행은 `exhibition.json`의 `server.venue`). 조작 화면에 venue 전환 UI는 없다. `--venue testroom`(기본값, `--venue` 없이 실행할 때)은 기존 절차형 테스트 방으로 fallback·test fixture로 남겨 두었다(실제 전시장 아님).

- 전시 실행 설정 `exhibition.json`: `venue: m30`, `mapping_file: data/m30/mapping.json`, `simulator_file: data/m30/simulator.json`. `data/m30/mapping.json`이 아직 없으면 예전 공용 `data/mapping.json`을 한 번 복사해 시작한다(`legacy_mapping_file`, 원본은 그대로). venue마다 다른 파일을 쓴다.
- 조작: 버튼을 누르고 있는 동안 움직이고 손을 떼면 감속해 멈춘다(자유 드래그·지도·방향 슬라이더·±15°·속도 조절 UI 없음). 버튼 배치: 윗줄 ↺ 좌회전 · ▲ 전진 · ↻ 우회전, 가운데 ◀ 좌이동 · ▶ 우이동(방향은 그대로 두고 장치 기준 왼쪽·오른쪽으로 평행이동), 아랫줄 ▼ 후진. 여러 버튼을 함께 누를 수 있다(예: 전진 + 우이동 = 대각선). 페이지는 누르는 동안 `{"op": "drive", "device", "move": -1|0|1, "turn": -1|0|1, "strafe": -1|0|1}`(strafe는 생략 가능, 예전 페이지 호환)를 0.2초마다 보내고, 서버가 움직임을 계산해 모든 화면에 같은 pose를 보낸다. 0.6초 안에 반복이 오지 않으면 뗀 것으로 본다(탭이 닫혀도 장치가 계속 가지 않음).
- 속도(고정값, **미확정 초기 실험값**, `simulator_store.py`의 `MOTION` 한 곳에서 바꿈): 전진 0.5 m/s, 후진 0.3 m/s, 가속 0.5 m/s²(약 1초에 최고 속도), 감속 1.0 m/s²(손 뗀 뒤 약 0.5초·12cm 미끄러짐), 회전 30°/s, 회전 가속 60°/s², 회전 감속 120°/s², 좌우 평행이동 0.3 m/s(가속·감속은 전후진과 같음), 미끄러짐 최소 각도 10°. 사람이 장치를 끄는 상황을 위한 보수적 값이며 실제 값은 사용자가 정하지 않았다.
- 충돌: 장치를 반지름 300mm 원으로 보고(`venue.py`의 `DEVICE_RADIUS_MM`, 실제 장치 크기 미측정 가정값) 벽·기둥·유리·커튼·이동식 벽체에 닿으면 접점까지 간 뒤, 남은 이동에서 면을 향하는 성분을 빼고 면을 따라 미끄러진다(전후진·좌우이동 모두, 혈·맥 같은 규칙). 면에 거의 정면(10° 안)으로 닿거나 미끄러지는 방향이 바로 다른 면에 막히는 오목한 모서리에서는 멈추고 속도 0. 구조물 안으로는 들어가지 않는다. 회전은 계속 된다. 멈춘 쪽 버튼에 빨간 테두리. `/api/simulator`의 `motion.<장치>.sliding`(미끄러지는 면)·`blocked`(멈춘 원인).
- 혈 기구 접속 / 해제(조작 화면, 혈 선택 시만 보임): 접속 = 사용 중, 해제 = 아이들링. 해제하면 mock ToF 새 프레임과 상향 거리 새 값이 수집되지 않고, `/status`(`collecting: false`, `hyeol`), `/inputs`(`hyeol`, 거리 채널 `paused`), 혈 기구 화면(배너 "아이들링 · 센서값 수집 멈춤", 마지막 프레임 흐리게), 블라인드 출력 진단 글자에 같이 나타난다. 상태는 서버에 저장되어 다른 화면·새로고침·재시작에서 같다. 장치 이동은 해제 중에도 가능하다. **시뮬레이션용 전환**이다: 실제 기구에서 접속 여부를 어떤 신호로 판별할지는 미결이며, 실제 장치 모드(`--mock` 없음)에는 적용하지 않는다(`/inputs`의 `hyeol.applied`).
- 센서 반영(`--mock`): ToF mock 카메라가 혈 pose(1.5m 높이, 정면, 기울기 0)에서 venue geometry를 raycast한다(pose 변경 재계산 약 2–8ms, 매 프레임 반영). 20m 거리 mock은 혈 위치 2.0m에서 수직 위로 천장(또는 위쪽 구조물 아랫면)까지의 거리다. M30은 자료로 확인되는 천장이 공식 높이 4.2m의 평평한 면뿐이라 **어디서나 2.20m**로 같다(천장 높이가 다른 구역이 있으면 값이 바뀌는 것은 테스트 전용 fixture로 확인). 천장을 모르는 venue에서는 값이 없다(None, 추정값을 만들지 않음). venue 모드에서는 테스트 방의 걷는 사람·흔들리는 물체를 넣지 않는다(건물만).
- 저장: `{"version": 2, "venue": "m30", "revision", "hyeol_attached": true, "devices": {"hyeol": {"x", "y", "heading"}, "maek": {…}}}`. x·y는 venue 평면 mm, heading 0 = +y, 90 = +x. 멈춘 pose는 바로, 움직이는 중은 0.5초 debounce로 저장, 원자적 저장·.bak·손상 복구는 mapping과 같다. 다른 venue의 파일이면 옆에 복사해 두고 쓰지 않는다. 예전 version 1 파일(venue 없음)은 testroom 파일로 읽는다.
- 공통 인터페이스: `<script src="/simulator.js"></script>` → `RipplesSim.connect(state => …)`(`/ws/simulator`), 읽기만 할 때는 `GET /api/simulator`(`venue`, `devices`, `motion`, `hyeol`, `motion_config`).

#### 공간 3D 확인 (`/venue3d`)

- 확인 도구다. 편집·생성·삭제·저장 기능이 없고, 서버에도 쓰기 endpoint가 없다(`GET /api/venue`만, POST는 404).
- `GET /api/venue`가 돌려주는 venue.py 결과(geometry.json 그대로의 `source`와, 다각형·solid 위쪽 높이를 계산한 값)를 그대로 그린다. 구조물 개수·이름을 화면 코드에 고정하지 않으므로 geometry.json에 solid를 더하면 같은 화면에서 보인다. `z1`이 없는 solid는 그 위치의 천장 높이까지(천장도 미확인이면 높이를 지어내지 않고 바닥 윤곽만) 그린다.
- 표시: 바닥(walkable 윤곽)과 1m 격자, 천장 윤곽선, solid 종류별 색(유리는 반투명, 색은 구분용이며 재질 아님), 혈(주황)·맥(파랑) 원기둥(반지름 300·높이 2,100mm 가정값)과 방향 화살표, 혈의 ToF 시야(1.5m, 70°, 4m)와 상향 거리센서 선, 사람 목업 실루엣(초록). 혈이 해제(아이들링)면 센서 선이 회색.
- `구조물 목록`: solid마다 id · 종류 · 상태(파일에 적힌 그대로) · 높이 출처 · 출처 문서. 누르면 3D에서 노란색으로 강조. 근사·미확인 목록과 장치 크기 가정도 같이 보인다.
- 조작: 한 손가락(마우스 왼쪽) 끌기 = 회전, 두 손가락 = 확대·축소와 이동, 휠 = 확대·축소, 오른쪽 버튼·Shift 끌기 = 이동, `전체 보기`, `위에서`. 3D 화면과 버튼 영역이 나뉘어 있어 서로 간섭하지 않는다.
- 장치 이동: 버튼은 `simulator.js`의 `RipplesSim.bindDrivePad`를 `/simulator`와 같이 쓰고, 속도·관성·충돌·미끄러짐은 서버(`simulator_store.py`)가 계산한다. pose는 `/ws/simulator`의 같은 상태 하나뿐이다(따로 저장하지 않음).

#### venue geometry (`venues/<id>/geometry.json`, 형식 `ripples-venue/1`)

Mac·Windows가 같은 JSON을 읽는다(SKP·PDF는 런타임에 읽지 않음). 2.5D: 바닥 높이, 천장 높이(구역별로 바꿀 수 있고 `null` = 미확인), 수직 solid(평면 `rect`/`poly` + `z0`–`z1`, `z1: null` = 천장까지). 항목마다 출처(`ref`)와 상태(도면 실측 / 근사 / 미확인)를 적는다. `venue.py`가 읽고 검증·충돌·상향 거리·ToF raycast를 맡는다.

## Windows 전시 실행 (전시 컴퓨터에서 SSH로 mock 서버·원격 mapping까지 확인 · Edge 출력 창은 프로세스 수준만, 화면 표시와 현장 LAN 접속은 아직 확인 안 함)

Mac에서 개발한 같은 폴더를 Windows 전시 컴퓨터에 복사해 실행한다. 관리자 권한·개인 계정 없이 이 폴더 안에서만 동작하도록 만들었다.

설치 (처음 한 번, 인터넷 필요):

1. Python 3.9 이상을 현재 사용자 범위로 설치. 전시 컴퓨터에는 `winget install -e --id Python.Python.3.12 --scope user`로 Python 3.12.10을 설치했다(`C:\Users\Admin\AppData\Local\Programs\Python\Python312\python.exe`, py launcher 포함, 관리자 권한 없음). `WindowsApps` 폴더의 `python.exe`는 Microsoft Store 바로가기라 쓰지 않는다.
2. 이 폴더에서 명령 프롬프트: `py -3 -m venv .venv` → `.venv\Scripts\activate` → `pip install -r requirements.txt` (numpy, opencv-python-headless).
3. 브라우저는 Windows 기본 Edge 또는 Chrome을 쓴다(`exhibition.json`의 `browser.path`가 `auto`면 표준 설치 경로에서 찾음).

설치 당일 `exhibition.json`에서 바꾸는 값:

- `outputs[].window`: 출력 창의 `x`, `y`(Windows 가상 화면 좌표, 예: 주 모니터 1920px 오른쪽 모니터면 `x: 1920`), `width`, `height`. `null`이면 브라우저가 정한 위치에 연다.
- `outputs[].url`: 기본 `/display/blind?space=a&clean`, `/display/blind?space=b&clean`(옛 `/output/<역할>?space=…&clean`도 동작). `enabled: false`로 출력 하나를 끌 수 있다.
- `browser.kiosk`: `true`면 주소창 없는 전체 화면(kiosk), `false`면 창 모드(app).
- `server.port`(기본 8000), `server.mock`(Windows에서는 `true`, ToF 카메라는 Pi 전용).

실행 순서:

1. `start_exhibition.bat` 더블클릭(또는 `py -3 exhibition.py start`): 서버를 켜고 응답을 기다린 뒤 출력 창을 하나씩 연다. 출력 창마다 이 폴더의 `run\browser-<이름>\` 프로필을 쓴다(개인 브라우저 프로필과 분리).
2. 휴대폰을 같은 LAN에 연결하고 `http://<전시PC_LAN_IP>:8000/mapping?test`.
3. `stop_exhibition.bat`(또는 `exhibition.py stop`): 출력 창을 닫고 1초 기다린 뒤(마지막 mapping 저장) 서버를 끈다. 상태 확인은 `exhibition.py status`, 실행할 명령만 보려면 `exhibition.py start --dry-run`.

- 실행 기록과 서버 로그: `run\processes.json`, `run\server.log`.
- Windows 방화벽: 전시 컴퓨터에서는 방화벽 규칙을 추가하지 않고도 Tailscale(Private 네트워크) 경유로 8000에 접속됐다. 유선 이더넷은 Public 네트워크로 잡혀 있어, 현장 LAN에서 휴대폰 접속이 되는지는 아직 확인하지 않았다. 스크립트는 방화벽·Tailscale·SSH·Parsec 설정을 바꾸지 않는다.
- Windows에서 `stop`은 `taskkill /T`로 서버 프로세스 트리를 끝내므로(`.venv\Scripts\python.exe`는 실제 Python을 자식 프로세스로 띄움), 드래그 중 마지막 0.5초 안의 값은 잃을 수 있다(손을 뗀 위치는 이미 저장됨).
- SSH로 실행할 때: Windows OpenSSH는 세션이 끝나면 그 세션에서 띄운 프로세스를 함께 끝낸다. `exhibition.py`는 서버와 출력 창을 세션 밖으로 분리해 띄우므로 SSH 연결을 닫아도 서버가 계속 돈다(전시 컴퓨터에서 확인).
- SSH로 `start`(출력 창 포함)를 실행하면 Edge는 Windows session 0(서비스·SSH용 비대화형 세션)에서 실행된다. 전시 컴퓨터에서 프로세스, kiosk 인자, 부스별 프로필, output A 페이지의 서버 연결까지는 확인했지만, 이렇게 띄운 창은 로그인된 바탕 화면에 보이지 않는다. 실제 화면에 띄우려면 로그인된 바탕 화면에서 `start_exhibition.bat`을 실행해야 한다(아직 화면으로 확인하지 않음). 원격 점검·조작은 `start --no-browser`로 서버만 켜고 Tailscale 주소로 한다.

SSH로 반복 실행·확인 (Mac에서, `<key>`는 전시용 SSH key):

```bash

ssh -i <key> Admin@<전시PC_tailscale_IP> "cd /d C:\\Users\\Admin\\tof-web-viewer && .venv\\Scripts\\python.exe exhibition.py start --no-browser"
```

`.venv`, `run/`, `__pycache__`, `data/`는 Mac에서 보내지 않는다(`data/mapping.json`은 전시 컴퓨터의 값이 기준).

### ToF mock (`mock_tof.py`)

실제 B0410 캡처가 아직 없어서, 실제 센서와 같은 값이 아니라 **저해상도 ToF 센서처럼 동작하도록 만든 물리 근사**다. 240×180, depth(mm)·confidence float32, 30fps, 실제 카메라 경로와 같은 형식으로 server.py에 들어간다.

- 장면: 바닥 1.2m 높이에서 8° 아래를 보는 고정 카메라. 바닥·천장·좌우 벽, 3.6m 뒤 벽(검은 포스터), 오른쪽 문 너머 7m 복도(범위 밖), 어두운 상자, 천천히 걷는 사람, 0.5초 만에 화면을 가로지르는 작은 물체(시간 필터·지연 확인용).
- confidence는 반사율 × 입사각 cos ÷ 거리²에 비례 → 먼 곳, 비스듬한 바닥, 어두운 면일수록 낮아져 confidence 기준(기본 30)에서 빠진다.
- 공간 모드(`--venue m30`)는 B0410 Far mode(최대 4m)에 맞춘 감도(`mock_tof.AMP_K_FAR`)를 쓴다. 가장 어두운 면(암막커튼, 반사율 0.06 가정)도 정면 4m에서 confidence 약 34로 기준 30을 넘어, 정면의 벽·커튼·사람이 1m부터 4m 바로 앞까지 실제 거리로 보이고 4m를 넘으면 무데이터(검정)다. 수평 1.5m 높이 카메라라 바닥은 화면 아래쪽에 3.2–4m로만 보인다. 예전 감도(`AMP_K`, 테스트 방은 그대로)에서는 커튼이 약 1.9m, 사람이 약 3.9m에서 빠지고 바닥은 보이지 않았다(2026-10-14 수정). 실제 B0410 캡처와는 아직 비교하지 않았다.
- 실제 카메라 경로(`server.py`)는 `Control.RANGE`를 4000으로 설정한다(Far mode). 실제 장치로는 확인하지 않았다.
- 픽셀마다 2×2 하위 광선을 위상(phasor)으로 섞는다 → 경계에 중간값(flying pixel)과 신호가 상쇄된 끊김이 생긴다. 가까운 물체와 먼 벽이 섞인 경계 픽셀은 두 거리 밖의 값이 나올 수 있다(실제 ToF에서도 생기는 현상, 3초에 약 100px).
- depth 흔들림은 신호가 약할수록(멀수록) 커지고, 시간 상관 잡음(AR(1) 0.8)이라 정지한 벽은 매 프레임 새로 튀지 않는다.
- 4m 밖 반사와 4m 근처에서 위상이 한 바퀴 돈 값은 depth 0(무효)·낮은 confidence로 내보내고, 가까운 값처럼 보이게 두지 않는다.
- 가정값(실제 B0410 값으로 확인하지 않음): 수평 화각 70°, 진폭 배율, 잡음 크기, depth를 광선 방향 거리(radial)로 냄. 실제 SDK가 수직 거리(Z)를 낸다면 평평한 벽의 CONTOUR가 원이 아니라 직선이 된다.
- 방은 변하지 않으므로 방의 픽셀 합을 한 번만 계산해 두고, 매 프레임 사람과 작은 물체가 덮을 수 있는 화면 영역만 다시 계산한다(전체를 매번 다시 계산한 결과와 비트 단위로 같음을 확인).
- 재현 확인: `python mock_check.py` (seed 7, 90프레임). 크기, 4m 처리, confidence와 무효 연동, 정지 배경 대 움직이는 대상, 거리별 잡음·결측, 경계, 이동 연속성, 같은 seed 재현, 생성 시간을 수치로 확인하고 하나라도 실패하면 exit code 1.
- 다른 포트: `python server.py --port 8080`

파이 데스크톱에서 모니터용 브라우저를 전체 화면으로 띄우기(서버 실행 후, 다른 터미널):

```bash
chromium-browser --kiosk --noerrdialogs --disable-infobars "http://localhost:8000/?kiosk"
```

배포판에 따라 명령 이름이 `chromium`일 수 있다. 키오스크 창은 `Alt+F4`로 닫는다.

## 화면 모드

```text
SENSOR      실시간 흑백 깊이 영상
CONTOUR     정면 거리 등고선
SIDE        선택한 행의 옆 단면
RELIEF 45°  깊이를 높이로 바꾼 입체 지형
```

**SENSOR**: 감각기구 모니터용. 실시간 깊이를 흑백으로 표시한다(가까울수록 밝게, 먼 거리와 무효 픽셀은 검정).
시간축 필터·공간 필터를 쓰지 않고 원본 프레임을 그대로 그려 지연이 가장 적고, 픽셀 구조가 보이도록 보간 없이 확대한다.
화면 중앙 5×5 픽셀 위치에 작은 네모 표시가 있다. 그 중앙값 거리(`840 mm` / `1.84 m` 형식)는 2026-10-15 밤부터 그림 위에 쓰지 않는다(사용자 요청). 값 자체는 프레임에 그대로 있고, 센싱 모니터·기구 화면 진단 줄의 "중앙 …"에는 계속 나온다.
측정값이 없는 픽셀(NaN, 0 이하, 4m 밖, 반사가 약해 confidence 미만)은 모든 모드에서 검정이다. 예전의 `데이터 없음 표시`(마젠타) 옵션은 없앴다(서버는 `nodata` 값을 받아도 무시).
CONTOUR·SIDE·RELIEF는 시간 필터·5×5 median을 거친 뒤에도 **이번 프레임에 값이 없는 픽셀은 값 없음으로 되돌려** 이전 프레임 값(잔상)이나 주변 값으로 채우지 않는다. 단, SIDE 그래프 아래로 흘러가는 지난 단면들은 이 모드의 기존 기록 표시라 그대로이며, 흐름 속도 1.0×에서 약 11초 뒤 화면 밖으로 사라진다(현재 단면과 미니맵은 바로 검정).

**CONTOUR**: 블라인드 투사용. 깊이를 `등고선 간격`(기본 200mm) 단위로 나눈 경계를 흰 선으로 그린다.
처리 순서:

1. NaN·무한대·0 이하·`먼 거리` 초과 픽셀 제거
2. confidence 미만 픽셀 제거
3. 최근 3프레임 시간축 중앙값 (`시간 필터` 토글, 기본 켬)
4. 5×5 중앙값 필터(외곽을 흐리지 않음)
5. 면적이 작은 등고선 제거

`시간 필터`를 켜면 깜빡이는 노이즈는 줄지만 빠르게 움직이는 물체는 약 1프레임 늦게 따라오고 모양이 줄어든다.
`--mock`의 빠르게 지나가는 작은 물체로 켰을 때와 껐을 때를 비교할 수 있다.
무효 픽셀은 "아무것도 없음"으로 처리되므로 큰 무효 영역(측정 범위 밖 배경, 검은 물체 등)은 외곽선이 생긴다.
`가까운 거리`보다 가까운 쪽에는 등고선을 그리지 않는다.
`슬랫 미리보기`는 데이터는 그대로 두고 최종 화면에 수평 검은 줄만 덧씌운다.
간격은 이미지 높이 대비 비율로, `server.py`의 `SLAT_PITCH`/`SLAT_GAP`(MJPEG)과 `index.html`의 `SLAT_PITCH`/`SLAT_GAP`(Canvas)을 함께 바꿔 실제 블라인드에 맞춘다.

### SIDE와 RELIEF 45°는 높이맵 표현이다

B0410의 240×180 깊이맵은 카메라에서 보이는 앞쪽 표면까지의 거리만 기록한다. 물체의 옆면이나 뒷면은 측정하지 않는다.
SIDE와 RELIEF 45°는 이 거리값을 화면의 "높이"로 다시 해석한 미디어아트 표현이고, 실제 3D 형상이나 포인트클라우드가 아니다(화면 상태 줄에도 `높이맵 표현 · 실측 3D 아님`이 표시된다).
가로축은 센서 이미지의 좌우 픽셀 위치일 뿐 실제 폭(mm)이 아니며, 가려진 면을 만들거나 메우지 않는다.

높이 = `(먼 거리 − 깊이) / (먼 거리 − 가까운 거리)` × 깊이 강조 배율. 가까울수록 높고, `먼 거리`는 바닥(0)이다.

**SIDE**: `단면 위치`(0–100%)로 고른 한 행(세로 스캔이면 한 열)의 깊이를 옆에서 본 선으로 그린다.
왼쪽 위 정면 미리보기에 선택한 행이 얇은 수평선으로 표시된다.
현재 단면은 회색 기준선 위에 그려지고, 4px 간격으로 남긴 이전 단면들이 아래로 흘러내리며 시간의 흔적을 남긴다(화면 아래 끝에 닿으면 사라짐, 최대 250줄).
아래쪽(오래된) 단면이 위쪽 단면을 가리는 순서로 그리지만, 현재 단면은 가려지지 않도록 맨 위에 그린다.

- `기준선`(0–90%, 기본 60%): 화면 아래에서부터 기준선 높이. 올릴수록 흘러내릴 공간이 커진다. 작업실에서는 그 레이어의 기준선 슬라이더나 숫자 칸으로 바꾼다.
- `흐름 속도`(0.25–4배, 기본 1배): 1배는 프레임당 1px(30fps에서 초당 30px). 기준선 60%·화면 높이 약 640px이면 잔상이 약 13초(1배), 51초(0.25배), 3초(4배) 동안 남는다.
- `세로 스캔`: 스캔선을 가로선(행) 대신 세로선(열)으로 바꾼다. `단면 위치`는 좌우 위치가 되고(50% = 가운데 열), 미리보기에 세로선이 표시된다. 그 열의 위→아래 깊이가 그래프의 왼쪽→오른쪽으로 그려진다. 방향을 바꾸면 잔상은 새로 시작한다.

줄 간격과 최대 줄 수는 `index.html`의 `SIDE_STEP`, `SIDE_MAX`로 바꾼다. 다른 모드로 바꾸면 흔적은 지워진다.
무효 픽셀과 confidence 미만 픽셀은 선을 끊어 비워 두고, CONTOUR와 같은 필터(시간 필터 토글, 5×5 중앙값)를 거친 깊이를 쓴다.

**RELIEF 45°**: 고정된 45° 위에서 내려다본 직교 투영이다.
CONTOUR와 같은 등고선(같은 간격, 같은 노이즈 필터, 작은 등고선 제거)을 각 거리 높이로 들어 올려 계단식 지형처럼 쌓는다.
낮은 층부터 그리고, 각 층 아래를 검게 채워서 앞쪽의 높은 층이 뒤쪽 선을 가린다.
높이는 등고선 간격 단위로 계단처럼 끊어진다(간격을 좁히면 매끄러워진다).
깊이 강조 배율을 바꾸면 높이와 바닥 면적의 비율이 바뀌고, 전체가 화면에 맞도록 크기가 다시 조정된다.
이미지 테두리를 따라가는 선은 CONTOUR와 같은 이유로 그리지 않는다.
슬랫 미리보기를 쓸 수 있다.

서버는 깊이 데이터(SIDE)나 등고선 좌표(RELIEF)만 보내고, 옆 단면과 45° 투영은 브라우저가 Canvas 2D로 그린다(외부 라이브러리나 CDN 없음).
등고선을 서버가 원본 240×180에서 계산해 좌표만 보내므로 120×90 다운샘플은 하지 않았다.

### 실제 3D 포인트클라우드 (아직 구현하지 않음)

Arducam SDK 문서(0.1.21)의 `Control`에는 `INTRINSIC_FX`, `INTRINSIC_FY`, `INTRINSIC_CX`, `INTRINSIC_CY`가 있다.
공식 예제 `open3d_preview/preview_pointcloud.cpp`는 이 값을 `getControl`로 읽어 100으로 나눠 Open3D 포인트클라우드에 쓴다.
서버는 실제 카메라에 연결되면 이 네 값을 읽어 터미널(`Intrinsics (SDK, /100): ...`)과 `/status`의 `intrinsics`에 표시한다(읽지 못하면 `null`).

이 값이 이 카메라 개체마다 보정된 값인지, 공칭값인지는 아직 확인하지 못했다.
B0410에서 그럴듯한 값(예: cx ≈ 120, cy ≈ 90, fx ≈ fy)이 나오는지 확인한 뒤에만 다음 변환으로 실측 포인트클라우드 모드를 추가하는 것을 제안한다.

```text
Z = depth
X = (u - cx) × Z / fx
Y = (v - cy) × Z / fy
```

그 모드에서도 앞쪽 표면만 있으므로 옆으로 돌리면 얇은 막처럼 보이고, 가려진 부분은 비어 있어야 정상이다.
값을 얻지 못하면 임의의 값을 넣지 않는다.

```bash
curl -s http://localhost:8000/status | python3 -m json.tool | grep -A5 intrinsics
```

## 조작

모드(SENSOR/CONTOUR/SIDE/RELIEF 45°), 가까운 거리, 먼 거리, confidence, 단면 위치(0–100%), 깊이 강조(0.5–3배), 등고선 간격(50–500mm), 선 두께(1–3px), 슬랫 미리보기, 시간 필터, 전체 화면.
각 조작은 해당 모드에서만 보인다:

- 단면 위치, 기준선, 흐름 속도, 세로 스캔: SIDE
- 깊이 강조: SIDE, RELIEF
- 등고선 간격, 슬랫: CONTOUR, RELIEF
- 선 두께, 시간 필터: CONTOUR, SIDE, RELIEF
iPhone Safari처럼 웹페이지 전체 화면을 지원하지 않는 브라우저에서는 이 버튼이 `화면 맞춤`으로 바뀐다. 조작 UI가 영상 위로 겹쳐 떠 있다가 2.5초 뒤 숨고, 화면을 탭하면 다시 나타난다. 주소창까지 없애려면 Safari 공유 메뉴의 "홈 화면에 추가"로 아이콘을 만들어 그 아이콘으로 연다.
폭 640px 이하(휴대폰)에서는 모드 버튼·전체 화면·상태 줄만 보이고, 나머지 설정은 `설정` 버튼으로 펼치고 접는다(기본 접힘, 기기마다 마지막 상태를 기억).
전체 화면이나 `?kiosk`에서는 2.5초 뒤 조작 UI와 커서가 숨고, 마우스를 움직이면 다시 나타난다.
설정은 서버에 하나만 저장되므로 맥에서 바꾸면 파이 모니터와 프로젝터 화면에도 바로 반영된다(모든 화면이 같은 모드를 보여준다).

HTTP로 직접 바꿀 수도 있다:

```bash
curl "http://ripples-tof.local:8000/config?mode=contour&interval=250&line=2&slats=1&temporal=0"
curl "http://ripples-tof.local:8000/config?mode=side&row=40&gain=1.5"
curl "http://ripples-tof.local:8000/status"
```

`/config` 파라미터: `mode`(sensor|contour|side|relief), `near`, `far`, `confidence`, `interval`, `line`, `slats`(0|1), `temporal`(0|1), `row`(0–100), `gain`(0.5–3), `base`(0–90, SIDE 기준선), `flow`(0.25–4, SIDE 흐름 속도), `vertical`(0|1, SIDE 세로 스캔). `nodata`는 예전 호환용으로 받기만 하고 화면에는 쓰지 않는다(무데이터는 항상 검정).

## 저지연 구조

```
카메라 스레드: requestFrame → 즉시 releaseFrame → 필터/등고선 → 최신 프레임 1개만 덮어쓰기
                                                     │ (클라이언트 I/O 없음)
접속별 송출 스레드: 최신 프레임만 꺼내 전송 ───────────┘
```

- **캡처와 송출 분리**: 카메라 스레드는 네트워크에 쓰지 않는다. 느리거나 멈춘 브라우저가 있어도 캡처 속도는 그대로다.
- **큐 없음**: 서버는 가장 최근 프레임 하나만 보관한다. 늦은 클라이언트는 중간 프레임을 건너뛴다.
- **WebSocket 흐름 제어**: 브라우저가 프레임을 받을 때마다 `next`를 보내고, 서버는 그때만 다음(최신) 프레임을 보낸다. 네트워크 버퍼에 쌓이는 프레임은 최대 1개다. 그리기는 `requestAnimationFrame`에서 가장 마지막에 도착한 프레임만 한다.
- **전송 데이터**: SENSOR·SIDE는 240×180 uint16 깊이(약 86KB), CONTOUR·RELIEF는 등고선 좌표만(수 KB) 보낸다. 모드는 서버에 하나만 있으므로 SENSOR일 때 다른 모드의 계산은 하지 않는다. 선은 브라우저 해상도에서 벡터로 그려 프로젝터에서도 선명하다.
- **MJPEG 개선**: JPEG 인코딩을 카메라 스레드에서 빼서 MJPEG 접속자가 있을 때만 프레임당 한 번 하고, `TCP_NODELAY`와 작은 송신 버퍼로 쌓임을 줄였다. 다만 브라우저 내부의 MJPEG 버퍼링은 서버에서 제어할 수 없다. 비교하려면 `http://ripples-tof.local:8000/?mjpeg`. MJPEG에서는 SIDE가 정면 흑백 영상 + 선택 행 표시로, RELIEF가 평면 등고선으로만 나온다(입체 표현은 WebSocket 화면 전용).

### 지연 측정값

상태 줄에 `캡처 N · 표시 N fps · 지연 N ms (처리 N)`이 표시된다.

- **지연**: 서버가 `requestFrame`에서 프레임을 받은 시각부터 브라우저가 Canvas에 그리기를 마친 시각까지(최근 1초 평균). 원격 접속일 때는 2초마다 ping/pong으로 맥과 파이의 시계 차이를 보정한다.
- **처리**: 캡처 후 필터와 등고선 계산까지 걸린 서버 시간(`--mock`에서는 mock 프레임 생성 시간도 포함, 생성만 Mac 약 4ms·Windows 전시 컴퓨터 약 4ms).
- **그리기**: 브라우저가 한 프레임을 Canvas에 그리는 데 걸린 시간.
- 포함되지 않는 것: 센서 내부 노출·처리 시간(ToF 하드웨어), Canvas 그리기 이후 실제 화면 출력까지(보통 vsync 1–2회, 16–33ms).
- MJPEG 모드(`?mjpeg`)에서는 표시 시각을 알 수 없어 지연을 측정하지 않는다.

### WebSocket 패킷 형식 (`/ws`, little-endian)

40바이트 헤더 `<4sBBHHIdfHHBBHHBBH`: `"TOF3"`, mode(0 sensor / 1 contour / 2 side / 3 relief), flags(bit0 슬랫, bit1 세로 스캔, bit2 데이터 없음 표시), width, height, frame_id, capture_ms(float64, Unix ms), center_mm(float32, NaN=없음), near, far, line, row(%), gain×100, interval, base(%), 0, flow×100.

- sensor, side: 이어서 `uint16[width*height]` 깊이(mm, 0=무효). sensor는 필터 없음이고 `먼 거리`보다 먼 값도 그대로 보낸다(화면에서는 검정). side는 필터 적용
- contour, relief: `uint32 n`, `uint32[n]` 각 선의 점 개수, `uint16[n]` 각 선의 거리 레벨(mm), `uint16[]` (x, y) 좌표(원본 240×180 픽셀 기준)

## 문제 해결

- **새 버튼이나 조작이 안 보임**: 파이로 다시 복사했는지 확인하고, 서버(`server.py`)를 `Ctrl+C`로 끈 뒤 다시 실행하고 브라우저를 새로고침한다. 화면 파일은 접속할 때마다 새로 읽지만, 서버 코드와 패킷 형식은 재시작해야 바뀐다.
- **`Address already in use`**: 서버가 이미 실행 중이다. `pkill -f server.py` 후 다시 실행.
- **`camera open failed`**: 케이블 방향과 연결을 확인하고, 다른 ToF 프로그램을 종료한 뒤 재실행. 계속되면 `sudo reboot`.
- **"카메라 끊김"**: 3초 이상 새 프레임이 없다는 뜻이다. 터미널의 `Camera error` 메시지를 확인하고 서버를 재시작한다(오류 후 자동 재연결은 하지 않음).
- **화면이 멈춤 / "서버 연결 끊김"**: 브라우저는 WebSocket이 끊기면 1초마다 자동 재접속한다. 계속되면 서버 터미널을 확인한다.
- **지연이 큼**: 먼저 `?mjpeg`이 아닌 기본 주소인지 확인한다. 원격 Wi-Fi보다 파이 모니터(`localhost`)가 훨씬 빠르다. CONTOUR에서는 `시간 필터`를 끄고 등고선 간격을 넓히면 처리 시간이 준다.
- **`ripples-tof.local` 접속 불가**: 맥과 파이가 같은 네트워크인지 확인하거나, 파이에서 `hostname -I`로 IP를 확인해 `http://<IP>:8000`으로 접속한다.
- **등고선이 지글거림**: confidence를 올리거나, 등고선 간격을 넓히거나, `시간 필터`를 켠다.
- **RELIEF가 너무 납작하거나 너무 뾰족함**: 깊이 강조 배율을 조절하고, `가까운 거리`/`먼 거리`를 실제 공간 범위에 맞춰 좁힌다(높이는 이 범위 기준으로 0–1).
- **SIDE 선이 자주 끊김**: 그 행에 무효·저신뢰 픽셀이 많다는 뜻이다. confidence를 낮추거나 단면 위치를 옮긴다.
- **물체가 검게 사라짐**: confidence를 낮추거나 `먼 거리`를 늘린다.
- **`ModuleNotFoundError`**: `source ~/tof-env/bin/activate`를 먼저 실행했는지 확인한다.
